# Round 7 (2026-11-16): the benchmark's schema, defined over the store by an agent

The owner's two rules for this round: "The 3rd party benchmarks are source of truth", and "When
given data in a relational schema that I want to compute against directly, the agent should define
the view definitions." FHIR-AgentBench's answers are SQL over MIMIC-IV's tables; its agents get
the same data as FHIR. So this round an agent first defines those tables over the FHIR store, and
question agents then answer in SQL over them. Model: Sonnet, as every round. Full tables:
`2026-11-16-round7-full.md`; the tables the setup agent wrote: `2026-11-16-tables/`.

## How the tables arm works

1. **Setup, once** (`fab/setup-tables`). One agent gets the schema (`fab/schema.md`), the
   workspace over the store and the toolkit's guides, and writes ViewDefinitions and SQL tables
   over them until the benchmark's own train-split queries, asked of the workspace unchanged, give
   the benchmark's answers (`./check`, which is `fab/check-tables`: no model in it). It took 64
   minutes and 55 turns, and ended at 2,074 of 2,098 train queries: 13 views and 15 `.sql` files,
   11 KB. The 24 it could not match are all prescriptions the FHIR export cannot reconstruct
   (requests with no dispense period; mixes of several ingredients). A second agent
   (`--amend`, 32 minutes) added the resource behind each row as a `fhir_id` column, holding the
   same 2,074.
2. **Examples, from the train split** (`fab/make-examples`): the 45 kinds of question, one or two
   worked examples of each, and the 31 kinds of time phrase with the condition each is written
   as. The benchmark states all of it; nothing is taken from a test question.
3. **A question** (`fab/run … tables`): the agent reads the example of its question's kind, fills
   in the query, runs it (about 1 s) and cites the `fhir_id` of the rows it used.

The tables are right before any question agent runs: asked the benchmark's own queries for the
150 development questions they give the benchmark's answer for 149, and for the 150 unseen ones
for all 150 (18 s for each set). What is left is the question agent writing the query.

## The gate

```sh
racket -l- fhir-examples/agent-bench/fab/gate [--slips N] RUN_DIR…
```
takes scored runs together and answers one question: is there anything this arm cannot answer?
It prints the score as scored; the set-aside questions apart; the questions in scope as right
every time, missed sometimes (a slip of one pass) or missed every time; what a question costs
(input tokens, turns, seconds); the citations' precision and recall. It passes when no in-scope
question is missed every time and at most N are missed sometimes (default 0). A question marked
wrong only for an answer that, word for word, was marked right in another run is listed apart
as judged both ways: the benchmark's judge is a model, and that is its disagreement with
itself, not a slip of the arm's (below, "The measurement with held answers").

## Defects the round found in the toolkit (fixed in fhir, with tests)

- **Kept rows were recomputed after any JSON file was written beside the sources, and in every
  copy of a workspace.** A kept view's key held each workspace definition file's time of writing
  and counted any `.json` as a definition. An agent that wrote its `answer.json` made the next
  query take two minutes. The key now holds real definitions (a JSON file only when it states a
  resource) by place and content.
- **A store being upgraded on first open refused the next process** ("database is locked"): three
  agents opened MedAgentBench's store at once, the first was rebuilding its date index (the
  zone-less date change of round 6), the other two failed after two seconds. Schema changes are
  now asked again inside a write transaction, and a writer waits up to a minute.

# Round 7 (2026-11-16): the benchmark's schema, defined over the store by an agent

The owner's two rules for this round: "The 3rd party benchmarks are source of truth", and "When
given data in a relational schema that I want to compute against directly, the agent should define
the view definitions." FHIR-AgentBench's answers are SQL over MIMIC-IV's tables; its agents get
the same data as FHIR. So this round an agent first defines those tables over the FHIR store, and
question agents then answer in SQL over them. Model: Sonnet, as every round. Full tables:
`2026-11-16-round7-full.md`; the tables the setup agent wrote: `2026-11-16-tables/`.

## How the tables arm works

1. **Setup, once** (`fab/setup-tables`). One agent gets the schema (`fab/schema.md`), the
   workspace over the store and the toolkit's guides, and writes ViewDefinitions and SQL tables
   over them until the benchmark's own train-split queries, asked of the workspace unchanged, give
   the benchmark's answers (`./check`, which is `fab/check-tables`: no model in it). It took 64
   minutes and 55 turns, and ended at 2,074 of 2,098 train queries: 13 views and 15 `.sql` files,
   11 KB. The 24 it could not match are all prescriptions the FHIR export cannot reconstruct
   (requests with no dispense period; mixes of several ingredients). A second agent
   (`--amend`, 32 minutes) added the resource behind each row as a `fhir_id` column, holding the
   same 2,074.
2. **Examples, from the train split** (`fab/make-examples`): the 45 kinds of question, one or two
   worked examples of each, and the 31 kinds of time phrase with the condition each is written
   as. The benchmark states all of it; nothing is taken from a test question.
3. **A question** (`fab/run … tables`): the agent reads the example of its question's kind, fills
   in the query, runs it (about 1 s) and cites the `fhir_id` of the rows it used.

The tables are right before any question agent runs: asked the benchmark's own queries for the
150 development questions they give the benchmark's answer for 149, and for the 150 unseen ones
for all 150 (18 s for each set). What is left is the question agent writing the query.

## What the prompts changed

- **First prompt** (136, 137): one file of examples to grep, and "adapt the query". Agents adapted
  freely. Seven of the 14 development misses were "this hospital visit" questions, where the
  benchmark means the visit with no discharge time recorded and agents took a visit whose
  discharge lies after the assumed current time.
- **Second prompt** (140 on development): the kinds and the time phrases in the prompt, a file per
  kind. Agents now read the right example but still rewrote it.
- **Final prompt** (144 to 145): "copy the example's query whole and change only three things":
  the patient, the names and values, the time conditions. Costs about 22k more tokens a question
  than the first prompt (the kinds and phrases are about 2.5k tokens in every turn's context).

## The fourth prompt (2026-11-17)

Four changes, each from a miss the third prompt's runs made every time or the judge marked:
"current" also for an ICU stay (`icustays.outtime IS NULL`); a name is looked up exactly as the
question words it, case aside, before any pattern (`5% dextrose` found `Dextrose 5%` by pattern
and not `5% Dextrose`); "last year", "in the last year", "the previous month" are the calendar
unit before the current one, as the train phrases write them; and the answer is the query's value
alone (the judge had marked "Yes: last RDW-SD 44.6 … is less than …" wrong against `[[1]]`).
All three of the questions those were written for are now right in both runs.

## What is missed with the fourth prompt

Eight of the 409 questions in both runs, none of which an agent can get from the train split:
- **Six of one kind**: "List the [daily|monthly|yearly] [min|max|average] volume of {output}
  output …". The kind exists only in the test split (7 questions), and its query looks the
  output's label up in lower case (`d_items.label = 'chest tube #1'`), which matches nothing in
  the data, so the benchmark's answer is "none". An agent finds the label and reports the volume.
- **One organism question**: for "since 09/2116" the train split's queries of this kind always
  stop at the assumed current time (27 of 27); the test and validation splits' never do (5 of 5),
  so the benchmark's "last test" is one dated after its own "now".
- **One admission type**: `EU OBSERVATION` against the tables' `OBSERVATION ADMIT`. The FHIR
  export keeps class, priority and admit source, which the setup agent's rule reads; no train or
  validation query contradicts that rule (207 of 207, 55 of 55).
One or two more a run are slips that the other run does not make (three in the six runs: a
`GROUP BY` day dropped, "today" dropped, a "this hospital encounter" not applied).

The tables are not what is missed: asked the benchmark's own queries they give its answer for
**408 of the 409** test questions (the admission type), 419 of 424 validation queries and 2,074
of 2,098 train queries. Every table miss outside the test split is a prescription.

## Plan for what remains

In order of what it is worth. Items 1 to 3 need a decision; 4 to 7 are work.

1. **The lower-case label kind (6 to 7 questions, 1.7% of the split).** Nothing in the train or
   validation split shows it, so the only rule that gets it is one read from the test split.
   Proposed: do not add one; report the score as scored and, beside it, with those seven set
   aside; send the benchmark's authors the seven question ids and the one-line cause (the label
   literal is lower-cased in that template's query). If they correct the truth, the answers the
   agents already give become right.
2. **Hold the tables to the relational data itself.** The benchmark's database is built from the
   MIMIC-IV Clinical Database Demo, which is open on PhysioNet (reachable from here).
   With it, `check-tables` can compare each table row for row instead of through 2,098 queries.
   That settles the two table questions queries cannot: whether anything in the FHIR export tells
   `EU OBSERVATION` from `OBSERVATION ADMIT` (first location does not: it is the Emergency
   Department for both), and whether the prescriptions the tables get wrong (24 of 455 train
   queries, 5 of 84 validation, none of the test split's so far) can be rebuilt from
   MedicationDispense or MedicationAdministration. One amending setup agent per table with the
   row check as its gate, an hour each; where the export does not carry the fact, it is recorded
   as a limit of the export. It needs a yes: it is a new download, and it uses data a user "given
   a relational schema" may not have.
3. **The organism question's upper bound (1 to 2 questions).** Leave it. The only source that
   shows the test form is the validation split, three questions against the train split's 27.
4. **Slips (about one a run of 150).** A check the agent runs on its query before answering:
   the query with its literals taken out, set beside the example's the same way, and each clause
   the example has and the query lacks named (`GROUP BY`, `dischtime IS NULL`, a time phrase in
   the question with no condition). It is `check-tables`' normalising with a diff after it.
5. **Citation recall (0.88 to 0.91).** Three table shapes, not agents: `transfers` cites the
   Encounter where the benchmark cites the Location, a microbiology row the test and not the
   organism, a prescription the ingredient's Medication. The train split has the benchmark's
   resource ids: `check-tables` gets a mode that compares a query's rows' `fhir_id`s with them,
   and an amending setup agent fixes the three with that as its gate. For an aggregate over many
   rows the agent should cite every row: one more line in the prompt (the second query with the
   same conditions already exists).
6. **Tokens (73k a question; the first prompt: 51k).** The kinds and the phrase list are in every
   turn's context. Two things to measure: the phrase list as a file read once the kind is known
   (it is 1.2k tokens five times), and the `fhir_id`s selected in the answering query (one turn
   fewer). Target: under 60k at the same score.
7. **Reporting.** The whole test split has now been run (twice); the validation sample has not
   been run with the tables arm, and other arms were last run in round 4. One more full pass
   after items 4 to 6, three runs, is the number to publish.

## What was missed with the third prompt

Development, both final runs (4): two questions whose benchmark query looks a label up in lower
case and so finds nothing, where an agent finds the label (`chest tube #1`, `emesis`; the unseen
set has two more: `l pleural #1`, `or urine`) — the benchmark's answer is "none" and no rule an
agent could follow gives it; an admission type the FHIR export does not carry (`EU OBSERVATION`
and `OBSERVATION ADMIT` are both an observation encounter with routine priority); one organism
question where the agent's query differs from the example's. One run only (3): two right answers
the judge marked wrong ("Yes: last RDW-SD 44.6 … is less than …" against `[[1]]`), one label not
found. Unseen, both runs (5): the two lower-case labels, a "current ICU stay" question, a total
dose and a "was the patient in the hospital last year"; in one run also a question with two daily
weights where the agent led with one.

Resource citations: precision 0.98 to 1.00, recall 0.88 to 0.92 (round 6: 0.89 and 0.83). The
recall misses are three shapes of table, not agents: `transfers` cites the Encounter where the
benchmark cites the Location; `microbiologyevents` cites the test's Observation and not the
organism's; `prescriptions` cites the ingredient's Medication where the benchmark sometimes cites
the mix. The train split has the benchmark's resource ids, so `check-tables` could hold the tables
to them as it holds them to the answers. Not done.

## Tokens

The first prompt is the cheapest arm so far for what it gets right: 56k input tokens per correct
answer (workspace, round 6: 70k). The final prompt gets eight or nine more questions right and costs 75k
per correct answer. A question is five turns: read the example and look up names, run the query,
fetch the `fhir_id`s, write the answer, close.

## Defects the round found in the toolkit (fixed in fhir, with tests)

- **Kept rows were recomputed after any JSON file was written beside the sources, and in every
  copy of a workspace.** A kept view's key held each workspace definition file's time of writing
  and counted any `.json` as a definition. An agent that wrote its `answer.json` made the next
  query take two minutes. The key now holds real definitions (a JSON file only when it states a
  resource) by place and content.
- **A store being upgraded on first open refused the next process** ("database is locked"): three
  agents opened MedAgentBench's store at once, the first was rebuilding its date index (the
  zone-less date change of round 6), the other two failed after two seconds. Schema changes are
  now asked again inside a write transaction, and a writer waits up to a minute.
